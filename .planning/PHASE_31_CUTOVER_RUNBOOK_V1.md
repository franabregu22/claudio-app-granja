## 0B. Auth migration runbook (D-PC-7, Supabase-supported data migration)

**Mechanism:** the official Supabase CLI 2.119.0. Flags verified with `supabase db dump --help` on 2026-10-01: `--db-url`, `--data-only`, `--schema`, `--exclude`, `--use-copy`, `--file`, `--dry-run`. Restore with `psql`.

**Included auth data:** `auth.users`, `auth.identities`. Add `auth.mfa_factors` only if the counts export shows MFA factors > 0; the code uses no MFA.

**Excluded** (sessions / tokens / platform-owned; listed against the target Auth version, local stack 2026-10-01):
- `sessions`, `refresh_tokens`, `flow_state`, `one_time_tokens`, `mfa_amr_claims`, `mfa_challenges`, `audit_log_entries`;
- `oauth_authorizations`, `oauth_client_states`, `oauth_clients`, `oauth_consents`, `custom_oauth_providers`;
- `saml_providers`, `saml_relay_states`, `sso_domains`, `sso_providers`;
- `webauthn_challenges`, `webauthn_credentials`;
- `instances`, `schema_migrations` (never overwrite the target Auth version).

**Order:**
1. Fresh project.
2. `target-migrations` 0001→0070 (ledger = files).
3. Auth restore.
4. Phase 26 runner, cutover mode (`perfiles` with the same ids, then business data).
5. Verify.

The target has no trigger on `auth.users` / `auth.identities` and no public FK to `auth.users`, so steps 3 and 4 do not constrain each other mechanically. Step 3 goes first so the runner can verify the users and fail closed.

**Procedure** (owner-run in their own shell; the dump file holds password hashes, so it is SENSITIVE: never committed, never pasted, deleted after the window):

1. **Counts only, read-only, legacy.** `auth.users` count; rows per `auth.identities.provider`; unconfirmed users; `auth.mfa_factors` count; users without a `perfiles` row. The owner decides on any extra users.
2. **Export.** Check the generated script first with `--dry-run`:
   `supabase db dump --db-url "<LEGACY_DB_URL>" --data-only --use-copy --schema auth -x auth.sessions,auth.refresh_tokens,auth.flow_state,auth.one_time_tokens,auth.mfa_amr_claims,auth.mfa_challenges,auth.audit_log_entries,auth.oauth_authorizations,auth.oauth_client_states,auth.oauth_clients,auth.oauth_consents,auth.custom_oauth_providers,auth.saml_providers,auth.saml_relay_states,auth.sso_domains,auth.sso_providers,auth.webauthn_challenges,auth.webauthn_credentials,auth.instances,auth.schema_migrations -f auth_data.sql`
   (If MFA count = 0, also exclude `auth.mfa_factors`.)
3. **Rehearsal first.** Restore into the **local** stack after `db reset` + 0001→0070. Then: the counts match step 1; every legacy id is present; a login with a known test credential works. Only then go to production.
4. **Restore into the target:**
   `psql "<TARGET_DB_URL>" -v ON_ERROR_STOP=1 --single-transaction -c "SET session_replication_role = replica" -f auth_data.sql`
   Run as the `postgres` role of the new project. If the platform refuses `session_replication_role` for that role, stop: that is an owner / support action, not a workaround.
5. **UUID equality.** Compare the sorted `auth.users.id` lists (ids only, no emails) between legacy and target; they must be identical.
   - Count `auth.identities` per provider: equal on both sides.
   - After the runner: every `perfiles.id` has an `auth.users.id`, every intended user has a `perfiles` row, and no `@example.invalid` email exists.
6. **Login verification.** Each V1 user (5) signs in on the target app (email + password, existing password). `current_app_role()` gives the expected role: 4 ADMIN, 1 OPERATOR, or the owner's final list.
7. **Old sessions.** Invalidated by design: the session tables are not copied and the JWT signing differs, so legacy tokens and refresh tokens are rejected by the target.

**Rollback implications:**
- Legacy Auth is untouched, so a rollback A / B leaves legacy logins intact.
- A password changed in the target after the switch does not exist in legacy (case C).

**Blockers:**
- the counts export (owner);
- the local rehearsal of steps 2–5 with the real dump (owner-run export, handled as sensitive);
- confirming the restore privileges on the new project.

## 0E. Webhook switch plan

**Principle (ADR-003 D8 / ADR-006 §11):** a single MP authority at every moment. Legacy is the authority until the switch; the target is the authority after it. **No dual-delivery window:** MP sends to one URL. Dual processing would count the same payment in two ledgers with independent openings, so it is **unsafe** and not proposed.

**Order:**
1. **FREEZE** (users stop writing to legacy; the legacy MP webhook keeps receiving, so legacy stays complete up to the boundary).
2. **Boundary instant = MP opening.** The owner records the MP Account Money balance at the boundary (ADR-006 gate 3) **at the same moment** as the final legacy snapshot.
3. Target data migration with the openings (0F) and the Auth restore (0B).
4. Target worker readiness: the 0D steps 1–2 checks pass.
5. **SWITCH, one step:** MP panel webhook URL → target `mp-webhook` **and** the Netlify release that removes the legacy webhook / sync functions and the scheduled sync.
   - Between steps 2 and 5, any MP notification still lands in legacy (read-only for users but the webhook writer is still live). It belongs to the pre-boundary side **only if** its money is inside the opening. That is the G-7 exposure.
6. **Smoke:** ADR-006 gate 2, one real payment reaches `POSTED` on the target with no client attribution. Gate 4: no `FAILED_PERMANENT`, no unresolved `DISCREPANCY`, no ERROR source after the boundary.

**Duplicate-risk controls:**
- one URL at a time;
- the legacy writer is removed in the same release;
- target idempotency (source identity, delivery dedup, `external_ref` uniqueness) for MP retries reaching the target;
- G-7: the ADR-017 backend boundary classifies pre-boundary payments / report rows as `PRE_CUTOVER_INCLUDED_IN_OPENING_BALANCE` (no movement).

**C. Auth dump** (official CLI; sensitive file, outside the repository, mode 600, never committed, never printed):

| Rule | Detail |
|---|---|
| Included | `auth.users`, `auth.identities` |
| Conditional | `auth.mfa_factors`, **only** if the inventory shows `mfa_factors > 0`: `EXCL=$(node $A exclusions $LEG --allow-mfa yes)`, then `check-dump … --allow-mfa yes`. Legacy has `mfa_factors = 0`, so it stays excluded. |
| Excluded | everything else in `auth`: sessions, refresh tokens, flow state, one-time tokens, instances, schema_migrations, audit log, MFA factors / challenges / AMR claims / recovery codes, OAuth / SAML / SSO / SCIM / WebAuthn, and any future table |
| Unknown / new legacy tables | `exclusions` builds `-x` from the legacy catalog, so tables added by the hosted Auth version are excluded automatically.
