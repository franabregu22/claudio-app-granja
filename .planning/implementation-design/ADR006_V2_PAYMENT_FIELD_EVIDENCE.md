# ADR-006 — V-2 Payment Field Evidence

## 1. STATUS

**FINAL GATE (2026-09-28): V-2 VERIFIED for Step 6 (`api_payment` inbound approvals), with refunds and disputes fail-closed.** See §15. §15 supersedes the historical status below and the §13 contract.

*Historical status (first evidence pass, 74caa01):* **PARTIAL — V-2 does NOT unblock Step 6.**

Established, both documented and observed:
- gross amount;
- net amount;
- the gross → net identity;
- the approval date;
- `status` / `status_detail` / `operation_type` values for the observed shapes.

Not established:
- the per-component fee / tax breakdown. The only source is `charges_details`, which is undocumented. `fee_details` is documented but always empty. `taxes_amount` contradicts the observed tax.
- `payer.id`: the documented type differs from the observed type.
- `external_reference`: never observed with a value.
- refunds: not observed; no documented authoritative transition date.
- chargeback / mediation: not observed.

Details are in §12.

## 2. AUTHORIZATION AND SAFETY

- **Date:** 2026-09-28.
- **Authorization:** the owner explicitly authorized Step 5 / V-2, read-only against the owner's production Mercado Pago account.
- **Credential:**
  - `MP_ACCESS_TOKEN` was read only from the process environment.
  - It was never printed, logged, written or committed.
  - A local client sent it only as the `Authorization` header of GET requests.
  - The client allowed three path classes: `/v1/payments/search?…`, `/v1/payments/{id}` and `/v1/payments/{id}/refunds`.
  - `redirect: 'error'` was set.
- **Requests: 31 in total, all `GET`, all HTTP 200.** No other HTTP method was used.
  - **21 × `GET /v1/payments/search`** (pages of 100):
    - used only to locate representative ids;
    - results were projected in memory to class counts;
    - nothing from the search results was persisted except ≤10 candidate ids (scratch, deleted).
    - The newest 1 000 results cover 2026-08 to 2026-09. The index was stopped there to avoid crawling the account.
  - **10 × `GET /v1/payments/{id}`:** the real payment resources inspected (the cap).
  - `GET /v1/payments/{id}/refunds` and `GET /v1/chargebacks/{id}`: **not called.** No refund or dispute example was found.
- **Zero writes** to Mercado Pago. No POST, PUT, PATCH or DELETE. No Supabase production contact.
- **Raw data:**
  - The raw responses of the 10 payments were cached only in a scratch directory outside the repository, then deleted before completion.
  - No raw response is in git.

## 6. GROSS / FEE / TAX / NET ARITHMETIC

Signs and values are shown as returned. `Σcoll` is Σ `charges_details[].amounts.original` where `accounts.from = "collector"`. `Σpayer` is the same sum where `accounts.from = "payer"`.

| Sample | transaction_amount | Σcoll (name) | net_received_amount | gross − Σcoll = net? | total_paid_amount | gross + Σpayer = total_paid? |
|---|---|---|---|---|---|---|
| A1 | 15000 | 90 (`tax_withholding_collector-debitos_creditos`, base 15000, rate 0.6) | 14910 | 15000 − 90 = 14910 ✓ | 15000 | ✓ |
| A2 | 224000 | 1344 (same, rate 0.6) | 222656 | ✓ | 224000 | ✓ |
| B1 | 14000 | 84 (same) | 13916 | ✓ | 14000 | ✓ |
| C1 | 10 | 0.06 (same) | 9.94 | ✓ | 10.7 | 10 + 0.70 (`processing_fee`, from payer) = 10.7 ✓ |
| C2 | 36000 | 216 (same) | 35784 | ✓ | 38516.4 | 36000 + 2516.4 (`processing_fee`, from payer) = 38516.4 ✓ |
| D1 | 468000 | 2808 (collector withholding) | 465192 | ✓ | 470808 | 468000 + 2808 (`tax_withholding_payer-debitos_creditos`) = 470808 ✓ |
| E1 | 15000 | 90 | 14910 | ✓ | 15000 | ✓ |
| F1 | 6500 | 39 | 6461 | ✓ | 6500 | ✓ |
| H1 | 200000 | 0 (`charges_details = []`) | 200000 | ✓ | 200000 | ✓ |
| G1 (rejected) | 14000 | 84 listed | **0** | ✗ (not applicable: rejected) | 14000 | — |

**Result (9/9 approved samples):**
- `transaction_amount − Σ charges_details[from=collector].amounts.original = transaction_details.net_received_amount`
- `transaction_amount + Σ charges_details[from=payer].amounts.original = transaction_details.total_paid_amount`

**Classification observed:**
- Customer gross: `transaction_amount`.
- Mercado Pago fee charged to the collector: **none observed**. No `fee` charge had `from = "collector"`, and `fee_details` was always empty.
- Financing / processing charges: `charges_details` `type = "fee"`, `name = "processing_fee"`, **borne by the payer** (`from = "payer"`). They are not collector money.
- Taxes / withholdings on the collector: `charges_details` `type = "tax"`, `name = "tax_withholding_collector-debitos_creditos"` (0.6 % of `transaction_amount`).
- Withholding on the payer: `tax_withholding_payer-debitos_creditos` (not collector money).
- Net received: `transaction_details.net_received_amount`.

**Why the components are not frozen:**
- The per-component split exists only in `charges_details`, which no official reference documents.
- The documented `fee_details` is empty for every observed payment.
- The documented `taxes_amount` is 0 although a 0.6 % tax is withheld: documentation and observation disagree.

Only the **aggregate** collector deduction (`transaction_amount − net_received_amount`) is supported by documented fields.

## 7. PAYER / EXTERNAL_REFERENCE

- **`payer.id`:**
  - Documented as a number (R1); observed as a digit string (10/10).
  - The value semantics are consistent, but the type disagrees, so this mapping is **AMBIGUOUS** and is not frozen.
  - No payer personal field is read or stored. The payer object also carries email, name, identification and phone; none of them was used.
- **`external_reference`:** documented (R1), but **null in 10/10 samples and in 960/960 indexed collector rows. NOT OBSERVED with a value.**
- **Effect on AUTO attribution:**
  - No V-2 evidence supports reading either field for AUTO attribution in Step 6.
  - ADR-006's optional attribution stays NONE / MANUAL until these are resolved.
  - Nothing here extends AUTO eligibility.

## 8. APPROVAL DATE

- **Candidates:**
  - `date_created`;
  - `date_approved`;
  - `date_last_updated` (documented as "last payment event"; not an approval date);
  - `money_release_date` (documented as the settlement / availability date).
- **Observed:**
  - `date_approved` = `date_created` in 5/9 approved samples, and 1–2 s later in 4/9.
  - `money_release_date` = `date_approved` in 9/9.
  - For the rejected G1, `date_approved` and `money_release_date` are null.
  - The format is always `yyyy-MM-ddTHH:mm:ss.SSS-04:00`.
- **Authoritative choice for the APPROVAL transition: `date_approved`.** R1 documents it as the approval date and states it can differ from the creation date; it was observed accordingly.

## 12. NON-FINDINGS / OPEN ITEMS

1. **Component source (blocks the FEE / tax split in Step 6).**
   - `charges_details` is undocumented.
   - `fee_details` is documented but empty.
   - `taxes_amount` is documented but contradicts the observation.
   - A decision is needed: accept the undocumented `charges_details` as evidence, rely on the V-3 report for components, or post only the aggregate deduction. This is an architecture / owner decision; V-2 does not make it.
2. **`payer.id` type mismatch** (documented number, observed string). AMBIGUOUS.
3. **`external_reference`:** never observed with a value.
4. **Refunds:** not observed. The authoritative transition date is BLOCKED (only `date_created` is documented). Partial / multiple refunds and refund-id stability are unproven.
5. **Chargeback / mediation:** not observed. `/v1/chargebacks/{id}` is documented but not exercised.
6. **Observed receipt types differ from the design's assumption** (not a V-2 decision; surfaced for the owner):
   - Every observed collector payment is a `money_transfer` (transfers received) or an `account_fund` (deposit into the account, 154/960).
   - Whether `account_fund` is a customer receipt or an own-funds movement is a business classification that ADR-006 has not stated.
7. **`collector_id` type mismatch** (documented string, observed number). This matters for the Step 8 worker; its design already compares `String(collector_id)`.
8. **Sample boundary:** the 12-month window was not fully indexed. The newest 1 000 results cover only 2026-08 to 2026-09. Absence of a class means NOT OBSERVED, not impossible.

| 15 | `account_fund` business classification | V-4: an inbound receipt (cvu, collector = account); not client evidence | **D** | treasury direction (collector) and client attribution are separate; no normalization rule depends on it | normalize as an inbound receipt; attribution CLIENT_UNASSIGNED unless deterministic evidence exists |
| 16 | `charges_details` | observed, undocumented | **B** / non-authoritative | not needed: documented gross / net plus the residual cover the movement | never read for amounts or classification; its values do not change the outcome |

### 15.1 Fail-closed rules for Step 6 (smallest coherent change to ADR006_RPC_CONTRACTS_V1 §40.2)

- **A snapshot with refund evidence** (`refunds[]` non-empty, or `transaction_amount_refunded ≠ 0`, or `status = 'refunded'`, or `status_detail` in the documented refund values, e.g. `partially_refunded`):
  - **ERROR `REFUND_UNSUPPORTED`** (REVIEW_REQUIRED);
  - no claim, no movement, no children;
  - refund discovery (`api_refund` sources) is **disabled**;
  - an APPROVAL claimed earlier stays untouched.
- **A snapshot in `charged_back` / `in_mediation`** (or a mediation `status_detail`):
  - no claim and no movement;
  - if the APPROVAL identity already exists → IGNORED `NO_NEW_TRANSITION`, with the derived CHARGEBACK alert (unchanged, R-7);
  - if it does not exist → ERROR `DISPUTE_WITHOUT_APPROVAL` (REVIEW_REQUIRED), because the approval amounts cannot be trusted from a disputed snapshot.
- **Re-enabling** `api_refund` and refund discovery requires a real refund example and an amendment that freezes the refund transition date.
